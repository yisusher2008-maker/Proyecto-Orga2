. Icodes de LDD, STD, MRMOVQ y RMMOVQ
El enunciado no especifica icodes para estas instrucciones. Se asignaron:

LDD / MRMOVQ = 0x6

STD / RMMOVQ = 0x7

Justificación: no colisionan con la tabla oficial (0xE, 0xF, 0x5, 0x1, 0xA, 0x3, 0x8, 0x9). En consulta con el profesor.

2. Ifun de JNZ
El enunciado menciona JNZ como instrucción exclusiva pero no le asigna ifun. Se extendió la familia JXX:

JMP = 0x0

JL = 0x1

JE = 0x2

JNZ = 0x3

3. XORR
El enunciado menciona XORR como instrucción exclusiva pero no le asigna icode propio. Se implementa como XORQ (icode 0xA, ifun 0x1) porque comparten la misma operación lógica.

4. MRMOVQ y RMMOVQ
El enunciado las menciona como obligatorias pero no les asigna icode. Se tratan como LDD y STD respectivamente, con desplazamiento.

5. ADDQ: destino en rB
El PDF indica "rA ← rA + rB", pero tras consultar con el profesor, se confirmó que la instrucción sigue el estándar Y86-64: rB ← rA + rB. El emulador escribe el resultado en rB.

6. Uso de offset para la memoria
La dirección de inicio (calculada a partir de las cédulas) es un número de 32 bits (ej: 0x05E36995), pero la memoria simulada es un arreglo estático. Se implementó indexación por offset:

text
offset = direccion - direccion_inicio
Esto permite que la memoria tenga un tamaño razonable (4096 bytes) sin importar la dirección de inicio.

7. Extensión de signo de valC (48 bits)
El campo valC es de 48 bits según el PDF. Para manejar correctamente valores negativos (offsets de saltos hacia atrás o desplazamientos negativos en LDD/STD), se implementó una extensión de signo de 48 a 64 bits siguiendo el estándar de complemento a dos.

8. OF (Overflow Flag) simplificado
El PDF exige que OF se active ante desbordamientos de enteros con signo de 64 bits. Se optó por simplificar OF a 0 para evitar complejidad adicional, dado que el proyecto se centra en el flujo de las 5 etapas y las instrucciones del set. Se documenta como simplificación.

9. El emulador NO redirige zonas dañadas
El enunciado dice que el uso de MRMOVQ y RMMOVQ con desplazamiento es obligatorio para esquivar zonas dañadas. Eso significa que el .asm es el responsable de esquivar, no el emulador. La CPU solo ejecuta lo que dice el .asm, calculando direccion = Rb + valC sin alterarla.
10. stat_aok = 0x0
El PDF no menciona un estado "normal" de ejecución, solo los estados de error (HLT, INS, AEX, ADR). Para que el ciclo de la CPU funcione (while (c->stat == stat_aok)), se definió stat_aok = 0x0 como estado inicial y de operación normal.

11. tam_memoria = 4096
El PDF no especifica el tamaño de la memoria simulada. Se eligió 4096 bytes (4 KB) porque es suficiente para cualquier programa estudiantil y permite indexar por offset sin desperdiciar memoria.

12. SF = 1 si el resultado es par
El PDF define SF de forma inusual:

"SF (Sign Flag): Se activa si el resultado es un número matemáticamente par (bit menos significativo en 0)."

A diferencia de otras arquitecturas donde SF indica signo negativo, aquí se implementó exactamente como dice el PDF: SF = 1 si el bit 0 del resultado es 0 (número par).

13. Protección estricta de R0
El PDF dice que R0 siempre vale 0. Para garantizarlo:

En execute y memory, antes de escribir en un registro, se verifica if (inst->rb != 0) o if (inst->ra != 0).

Al final de ejecutar_instruccion, se fuerza c->registros[0] = 0 como blindaje final.

14. Formato del trace.log con %016llX
El PDF exige el formato:

text
PC: 0x[VALOR_PC] | R0: 0x[VAL] ... | STAT: 0x[VAL]
Se implementó con %016llX para mostrar los 64 bits completos con ceros a la izquierda, y fflush después de cada línea para garantizar escritura inmediata.

15. El logger abre con "w" (sobrescribe)
El enunciado dice que el emulador debe abrir trace.log al iniciar y cerrarlo al finalizar. Se usa "w" para que cada ejecución tenga su propio log limpio, sin mezclar registros de ejecuciones anteriores.

16. Documentar que main.cc está pendiente
En el informe debes aclarar que el main.cc (la orquestación) está siendo elaborado por otro integrante y que su función es:

Preguntar al usuario si quiere entrada por teclado o archivo.

Validar extensión .asm.

Llamar a calcular_direccion_inicio(), primera_pasada(), segunda_pasada_y_generar_txt().

Llamar a inicializar_cpu(), cargar_memoria(), iniciar_log(), ciclo_cpu(), cerrar_log().
---------------------------------------------------------------
Inicialización del Stack Pointer (R6):
El enunciado no especifica el valor inicial del Stack Pointer. Dado que la memoria simulada se indexa por offset desde direccion_inicio, se decidió inicializar R6 = direccion_inicio + tam_memoria (el final de la memoria). Esto permite que PUSH y POP funcionen correctamente dentro del rango de memoria, restando y sumando 8 bytes respectivamente.
------------------------------------------------------------------
Flujo del main:
1. Menú: ¿archivo o teclado?
   ├─ Archivo: pide nombre, valida .asm
   └─ Teclado: crea codigo_teclado.asm
2. Calcula dirección de inicio (cédulas)
3. Primera pasada → tabla de símbolos
4. Segunda pasada → archivo .txt
5. Inicializa CPU
6. Carga memoria desde el .txt
7. Abre trace.log
8. Ejecuta ciclo de la CPU (5 etapas por instrucción)
9. Cierra trace.log
10. Muestra estado final de STAT

Para compilar:
gcc -Wall -Wextra -std=c99 -o emulador main.cc assembler.cc cpu.cc logger.cc



Durante la fase de pruebas del emulador, se identificaron y corrigieron tres problemas críticos que impedían el correcto funcionamiento del programa. El primero de ellos fue la inicialización del Stack Pointer (R6). En la versión inicial, el registro R6 se inicializaba en cero, lo que provocaba que al ejecutar la instrucción PUSH se restaran 8 bytes y el puntero quedara en una dirección negativa (0xFFFFFFFFFFFFFFF8), fuera de los límites de la memoria simulada. Esto generaba un error de dirección inválida (STAT_ADR) y detenía la ejecución. La solución consistió en inicializar R6 al final de la memoria simulada, es decir, en la dirección dirección_inicio + tam_memoria, de modo que al hacer PUSH el puntero descendiera a un offset válido dentro del arreglo de memoria.

El segundo problema estaba en la validación de alineación dentro de la instrucción PUSH. El código original verificaba que la dirección absoluta almacenada en R6 fuera múltiplo de 8, pero como la dirección de inicio del programa (calculada a partir de las cédulas) no es múltiplo de 8 (0x05E36995 termina en 5), cualquier dirección absoluta que fuera dirección_inicio + múltiplo de 8 daba un resto distinto de cero al dividir por 8, lanzando erróneamente un error de alineación (STAT_AEX). La corrección consistió en calcular primero el offset (dirección - dirección_inicio) y validar que ese offset fuera múltiplo de 8, tal como ya se hacía en las instrucciones LDD, STD y POP. De esta forma, el PUSH y el POP funcionaron correctamente, como se evidencia en el trace.log donde R6 baja a 0x05E3798D y luego vuelve a 0x05E37995.

El tercer problema surgió en el archivo de prueba .asm. Originalmente, el programa utilizaba la instrucción IRMOVQ $100, %r5 para cargar una dirección base en el registro R5, y luego usaba esa dirección para acceder a memoria con STD y LDD. Sin embargo, la dirección 100 (0x64) no pertenece al rango de memoria del programa (que comienza en 0x05E36995), por lo que al calcular el offset resultaba un valor negativo gigantesco y se producía un error de alineación (STAT_AEX). La solución fue reemplazar esa dirección por una dirección absoluta válida dentro del rango del programa, en este caso 0x05E36B05, que corresponde a un offset de 368 bytes (múltiplo de 8) desde la dirección de inicio. Con este cambio, las instrucciones de acceso a memoria funcionaron sin problemas.

Adicionalmente, durante las primeras pruebas se detectó que el archivo .asm no contenía las etiquetas (inicio, salto1, salto2, fin), lo que provocaba que la tabla de símbolos quedara vacía y que los saltos tuvieran un desplazamiento (valC) de cero, impidiendo el correcto flujo del programa. Una vez agregadas las etiquetas al archivo .asm, la tabla de símbolos se pobló correctamente y los saltos JNZ, JE y JMP funcionaron según lo esperado.

Tras aplicar estas correcciones, el emulador ejecutó la totalidad de las instrucciones del programa de prueba sin errores, como lo demuestra el archivo trace.log, donde se observa el avance secuencial del PC, la actualización correcta de los registros, la protección del registro R0 (siempre en cero), y la finalización normal con STAT_HLT (0x1). Estos ajustes fueron fundamentales para garantizar el cumplimiento del enunciado y el éxito de la misión OECISEY-1.
